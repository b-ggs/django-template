# Repository guidance

## Environment

- Development is Docker-first. Before the first `make build`, create the required untracked env file with `cp .env.example .env`; Compose fails when `.env` is absent.
- `make build`, `make start`, `make stop`, and `make sh` manage the stack. `web` is the only application container and stays idle until commands are run through a shell; Postgres, Redis, and MailDev are separate infrastructure services.
- Python dependencies are locked with `uv.lock` (Python 3.14); Node dependencies are locked with `package-lock.json` (Node 24). Do not hand-edit lockfiles.
- `manage.py` defaults to production-like `django_template.settings.base`. Local Compose gets `django_template.settings.dev` from `.env`; tests must explicitly use `django_template.settings.test`.

## Verification

- Full tests with running containers: `make test`; reuse the test database with `make test-keepdb`.
- Focus one Django test by dotted path: `docker compose exec web python3 manage.py test --settings=django_template.settings.test -v=2 path.to.TestCase.test_name`.
- CI installs with `uv sync`, then runs:
  - `uv run pre-commit run --show-diff-on-failure --color=always --all-files`
  - `uv run python3 manage.py makemigrations --check --noinput`
  - `uv run python3 manage.py collectstatic --noinput`
  - `uv run python3 manage.py test --settings=django_template.settings.test -v=2`
- Host-side tests require PostgreSQL and `DATABASE_URL`; use Redis and `REDIS_URL` for CI parity or tests that touch cache/Celery. CI also sets `SECRET_KEY`; its service definitions are in `.github/workflows/ci.yml`. Prefer Compose when these services are not already available.
- Pre-commit mutates files: Ruff fixes/formats Python, djLint reformats/lints Django templates, and Tombi formats TOML. Re-check the diff after running it.

## Project boundaries and generated files

- `django_template/settings/{base,dev,test}.py` define environment behavior; `django_template/urls.py` is the root HTTP/API router, and `django_template/celery.py` is the Celery entrypoint.
- The project uses the custom `users.User` model (`AUTH_USER_MODEL = "users.User"`); use Django's configured user model rather than importing the built-in `User`.
- Edit Tailwind input at `django_template/static_src/tailwind/styles.css`, not generated `django_template/static_built/`; build CSS with `npm run tailwind:build` (production Docker builds do this automatically). `static_collected/` is also generated by `collectstatic`.
- Model changes must include migrations. Ruff intentionally excludes `django_template/*/migrations/*.py`; CI separately rejects missing migrations.
